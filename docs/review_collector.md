# 외부 리뷰 수집기 — 수집 시점에 무엇을 잡아야 하는가

**이 문서가 답하는 질문: 원문을 저장하지 않으면서 리뷰 진위 축이 서려면 수집기가 수집하는
그 순간에 무엇을 뽑아 둬야 하는가.** 구현 문서가 아니라 수집기를 짜기 전에 정해 둘 것의
목록이다. 수집기는 아직 없다(2026-09-11). 지금 데모는 공개 데이터셋 파생물
(`data/amazon23/`)로 이 자리를 대신한다.

명세서 §42 `evidence.review_summary` · §8.5 분석 입력 계약 · `docs/decisions/0001~0002` 위에 선다.

---

## 0. 왜 "수집 시점" 인가

외부 리뷰는 **원문을 저장하지 않는다**(명세서 "리뷰 원문 보관 정책"). 그러면 진위 축이
쓸 수 있는 것은 수집 순간에 원문에서 뽑아 둔 **비원문 값**뿐이다. 나중에 "그 컬럼도 뽑아
둘걸" 은 성립하지 않는다 — 원문이 없다. 아래 목록에서 빠진 것은 **영구히 없는 것**이다.

관계·행동 축(7일 몰림 · 공유 리뷰어 · 계정 신규성)은 본문을 보지 않는 대신 **누가 · 언제**를
본다. 그 둘이 없으면 축이 서지 않고, 수집 시각(`collected_at`)으로 대체하면 한 번에 긁은
리뷰가 전부 "같은 날 몰림" 으로 보여 없는 것보다 나쁘다.

## 1. 리뷰 한 건마다 잡는 것

| 항목 | 저장 위치 | 규칙 |
| --- | --- | --- |
| 외부 리뷰 식별자 · 원문 링크 | `review_summary.external_review_key` · `original_url` | 재수집 시 같은 리뷰를 같은 키로. `(source_id, key, processing_version)` UNIQUE |
| **작성자 식별자의 소스별 솔트 해시** | `review_summary.author_ref` | `hash(salt[source_id] ‖ external_author_id)`. **원 식별자는 폐기**. 소스가 안 주면 NULL |
| **원 게시 시각** | `review_summary.review_posted_at` | 소스 표기 그대로 UTC 변환. 시간대·정밀도(날짜만인지)는 `analysis_snapshot`에. 없으면 NULL — `collected_at`으로 채우지 않는다 |
| 평점 | `normalized_rating` | 소스 척도 → 5점. 척도는 `source.rating_scale` |
| **대상 옵션(variant)** | `review_subject.variant_id` (없으면 `product_id`) | 소스가 옵션(용량·와트·색)을 구분하면 **반드시 옵션 단위로**. 상품 가족 단위로 묶으면 허위 여부 축의 스펙 대조가 성립하지 않는다(§3) |
| 구매 확인 표시 | `dataset.review_sample.purchase_verified` (표본화 시) | 소스가 준 의미 그대로. **양방향 모두 증거 아님** — 5점 쏠림 계층의 확인율이 기준선보다 높았다 |
| 이미지 **식별자** (파일 아님) | `analysis_snapshot.signals[image_ids]` | URL의 파일 ID 또는 해시. 재사용 축(같은 사진이 다른 계정에)용. 이미지 자체는 저장하지 않는다 |
| 본문 길이 · 도움됨 수 | `analysis_snapshot.signals` | 원문 특징 중 허용된 수치만 |
| **검증 가능한 주장** (수치+단위, enum) | `analysis_snapshot.signals[claims]` | "240mm까지만 됨", "SATA", "ATX" 처럼 **스펙과 대조 가능한 항목만**. 판정이 아니라 추출. LLM을 쓰면 추출에만 쓴다 |
| 대표 요약 | `review_summary.summary` | 기존 설계 그대로 |

**저장하지 않는 것:** 원문, 원 작성자 식별자, 이미지 파일, 다른 사용자를 특정하는 문자열.

## 2. 소스 단위로 정하는 것

- **솔트** — 소스마다 하나. 시크릿 저장소에 두고 **회전하지 않는다**(회전하면 같은 계정이
  다른 값이 되어 관계 축이 끊긴다). 유출 시에는 회전하고 그 시점 이전 관계 축은 버린다
- **부류 전체를 긁는다** — 대조군은 같은 부류(카테고리)의 중앙값이다. 데모 부품 51종만
  수집하면 "리뷰 30건+ 상품 N개" 가 안 나와 중앙값이 서지 않는다. 카테고리당 리뷰 30건+
  상품이 최소 수백 개는 있어야 한다(공개 데이터 PC 부품에서는 11,457개였다)
- **약관·허용 범위** — 소스별로 수집 허용 여부, 요약 저장 허용 여부, 작성자 식별자 해시
  보관의 허용 여부. 이 문서는 그 검토를 대신하지 않는다
- **중복 기록** — 같은 리뷰가 두 계정으로 나타나는 소스가 있다(공개 데이터에서 6.0M건 중
  247건). `external_review_key` 로 한 번, 타임스탬프·평점·길이 동일로 한 번 더 거른다

## 3. 옵션 단위가 아니면 안 되는 이유 — 허위 여부 축

리뷰의 "2TB" 를 스펙의 "1TB" 와 대조하려면 **그 리뷰가 어느 옵션에 달렸는지** 알아야 한다.
공개 데이터에서는 상품 가족(`parent_asin`) 하나에 용량 5종·와트 10종이 묶여 있어 와트·용량
규칙이 구조적으로 깨졌다. 팀 스키마는 `product_fact` 를 옵션 단위로 설계해 뒀으므로
("옵션 한정 fact 우선, 모델 공통 fact 다음") **수집기가 옵션을 잡기만 하면** 이 축은 제품
안에서 열린다. 대조 규칙 자체는 정밀도를 사람이 읽어 확인한 뒤에만 켠다.

## 4. 처리 순서

```
수집 (소스별 어댑터)
  → 원문 일시 처리: 요약 · 주장 추출 · 이미지 ID · 길이        ← 원문은 여기서 버린다
  → review_summary (author_ref · review_posted_at · variant 대상) + analysis_snapshot
  → 배치: 관계·행동 축 (src/workers/relation_axis.py) — 부류 대조군 중앙값 · 근거 카드
  → product_manipulation_risk → [3-B] 리뷰축 · S5 카드
```

관계 축 배치의 입력 형식은 지금의 엣지 표(`user · product · ts · rating · verified`)와 같다.
`author_ref` 를 `user`, `variant/product` 를 `product`, `review_posted_at` 을 `ts` 로 넣으면
그대로 돈다 — 그렇게 되도록 컬럼을 정했다.

## 5. 미결

- 소스 목록과 각 소스의 작성자·게시시각·옵션 노출 여부 (없는 소스는 그 축에서 빠진다)
- 주장 추출기의 정밀도 — 사람 판독 전에는 `claims` 를 **카드에 올리지 않는다**(관측 목록으로만 저장)
- 재수집 주기와 `processing_version` 올림 규칙
- 부류(카테고리) 정의 — 대조군 중앙값의 단위. `config/categories/*.yaml` 과 맞출지
