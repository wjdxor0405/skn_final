# Deal Ledger MMVP — 프로젝트 현황 (Claude Code 인계용)

> 이 문서는 별도 채팅 세션에서 진행된 기획·설계 논의 결과를 코드 작업 이어가기용으로 요약한 것입니다.
> 원본 회의록·기획 문서는 `docs/` 폴더에 함께 두는 것을 권장합니다 (§6 참고).

---

## 1. 프로젝트 한 줄 정의

AI 에이전트(셀러·바이어)가 자동으로 가격을 협상하고, 사람은 최종 승인만 하는 B2B 거래 플랫폼의 MVP.
해커톤(AWS 주최) 제출용이며, 팀 내부 기획 문서 `P0_확정안_v3.md`와 RFQ 전체 흐름도를 기준으로 개발 범위를 잡고 있음.

---

## 2. 아키텍처 — MMVP L0~L4 매핑

```
app/
  schemas.py    L0 — 품목/메시지타입(REQUEST·OFFER·ACCEPT·REJECT·SETTLED)/Envelope
  store.py      L1 — 거래 요약(SQLite) + 로그 파일 + 카탈로그 출처 전환(sqlite ↔ odoo)
  agents.py     L2 — 규칙 기반 에이전트 (RuleBasedSellerAgent/RuleBasedBuyerAgent)
  llm_agents.py L2 — OpenAI 기반 에이전트 (OpenAISellerAgent/OpenAIBuyerAgent)
  audit.py      감사자 — LLM이 floor_price/cap_price 규칙을 어기면 보정
  negotiate.py  L3 — 매칭·협상 오케스트레이션, 라운드 상한(MAX_ROUNDS=3)
  report.py     L4 — 로그 기반 자연어 요약 + 리포트 파일 생성
  main.py       API 엔드포인트 + 목업(static/index.html) 서빙

  odoo_client.py  Odoo JSON-RPC 클라이언트 (표준 라이브러리만 — 새 의존성 없음)
  feasibility.py  납품 가능성 검증 (재고·BOM·조달납기·제조 리드타임을 룰로만 판정)
static/
  index.html    4화면 GUI 목업 (납품가능성검증/셀러등록/구매요청/협상결과·승인)
scripts/
  seed_odoo_demo.py  Odoo 제조업 데모 데이터 시딩 (멱등)
```

**XML-RPC가 아니라 JSON-RPC인 이유**: Odoo의 XML-RPC 마샬러는 `None`을 못 싣는데
액션 메서드(`button_confirm` 등)는 대부분 `None`을 반환한다. 메서드는 정상 수행된 뒤
**응답 직렬화 단계에서만** Fault가 나서, 성공을 실패로 오인하기 쉽다.

**핵심 설계 원칙**: `store.py`의 메서드 시그니처(`register_seller`, `sellers_for`, `append`, `get_log`, `set_deal`, `get_deal`)가 고정되어 있어서, 저장 방식이 바뀌어도(인메모리→SQLite→Odoo) 이 파일 밖은 거의 안 건드려도 됨. Odoo 연동도 이 원칙대로 `store.py` 안에서 끝났다 — 단 하나의 예외가 MOQ로, Odoo에만 있던 제약이라 `negotiate.py`의 스크리닝에 한 절이 추가됐다. `agents.py`/`llm_agents.py`도 같은 인터페이스(`SellerAgentPort`/`BuyerAgentPort`)라 `NEGOTIATOR_MODE` 환경변수 하나로 전환.

## 3. 구현 완료 목록

- [x] L0~L4 전체 파이프라인 (등록 → 협상 → 승인 → 리포트)
- [x] 규칙 기반 협상 (rule 모드, 기본값, API 비용 없음)
- [x] OpenAI 기반 협상 (llm 모드, `NEGOTIATOR_MODE=llm` + `OPENAI_API_KEY` 필요)
- [x] 감사자 — LLM이 floor/cap 가격 규칙 위반 시 자동 보정, 로그에 `audit_note`로 남음
- [x] 협상 라운드 상한(3회) — 무한루프 방지
- [x] SQLite 연동 — 서버 재시작해도 카탈로그·거래 데이터 유지
- [x] `.env` 기반 환경변수 관리 (Windows/Mac/Linux 공통, `export` 불필요)
- [x] RFQ 필드 확장 — 품목·수량·상한가 + **사양·납기일수** 추가 (v3 D-02 일부 반영)
- [x] 매칭 조건에 재고·사양·납기 반영 — 조건 미달 셀러는 협상 라운드 진입 전 자동 제외
- [x] 실패 사유 2종 분리 — `NO_MATCH`(조건 맞는 셀러 자체 없음) vs `NO_DEAL`(협상은 했으나 가격 결렬)
- [x] Docker화 — Dockerfile, .dockerignore, 목업의 localhost 하드코딩 제거(상대경로로 전환)
- [x] `.gitignore` — `.env`, `data/`, `reports/` 등 제외
- [x] **Odoo 연동 (`CATALOG_SOURCE=odoo`)** — 공급처 단가표를 카탈로그로 읽음. 기본값 `sqlite`라 기존 동작은 그대로
- [x] **MOQ(최소주문량) 스크리닝** — 재고와 부등호 방향이 반대인 제약. Odoo `product.supplierinfo.min_qty`에서 옴
- [x] **낙찰 → Odoo 발주서 초안** — `origin`에 거래ID를 넣어 중복 생성 방지, chatter에 협상 라운드 전문 기록
- [x] **승인/거절 → 발주서 확정/취소** — 어느 화면에서 눌러도 두 시스템 상태가 갈라지지 않음
- [x] **납품 가능성 검증 (화면 0)** — BOM 전개로 자재 소요·부족·조달납기를 산출. v3 §2가 "LLM 없이 넣을 수 있는 유일한 검증"이라 한 자리
- [x] Odoo 쓰기 실패 격리 — Odoo가 죽어도 협상 결과는 보존되고 `po_error`로 화면에 표시

## 4. v3 확정안·흐름도 대비 — 아직 안 된 것 (우선순위순)

### 4-1. 다음 작업 후보 (구조 변경 필요, 중간 비용)
- [ ] **비교표 + 사람이 후보 중 직접 선택** — 지금은 시스템이 최저가 1건을 자동 확정 → 사람은 승인/거절만 함. v3·흐름도는 "여러 후보를 순위표로 보여주고 사람이 고른다" 구조를 요구함
- [ ] **동시 디스패치(경쟁 입찰) 구조** — 지금은 셀러 A를 끝까지 협상한 뒤 B로 순차 진행. 흐름도는 "적격 셀러 전원에게 동시 초대 → 각자 독립 제안 → 취합" 구조
- [ ] 승인 이력에 "누가" 필드 — 현재 승인자/역할 개념 자체가 없음 (정식 로그인 없이 이름 하드코딩 정도로도 P0 기준 충족 가능)

### 4-1-b. 보안 (EC2 배포 전 필수)
- [ ] **CORS·인증** — 지금 `allow_origins=["*"]` + 인증 없음인데, `odoo` 모드에서는 `POST /api/deals/{txid}/approve` 가 **Odoo 발주서를 확정**한다. 외부 노출 전에 오리진을 좁히고 승인 계열에 토큰을 둘 것 (`app/main.py` 상단 주석 참고)

### 4-2. 인프라 (다음 마일스톤, 지금 급하지 않음)
- [ ] AWS 실배포 (Dockerfile까지는 준비됨, 실제 EC2 배포·접속 검증은 아직 안 함)
- [ ] I-03 Bedrock + Strands SDK — **현재 OpenAI API 사용 중.** 해커톤이 AWS 주최라 SDK/Bedrock 사용이 채점에 영향 줄 수 있음, 팀 확인 필요
- [ ] 4프로세스(중앙·셀러2·바이어) 실제 분리 — 지금은 한 프로세스 안에서 함수 호출로 시뮬레이션

### 4-3. 뒤로 미룬 것 (v3 문서가 스스로 P2 이상으로 명시)
- 역할 4종 분리(구매담당자/승인자/판매담당자/감사거버넌스) — 지금은 역할 구분 없음
- 정식 인증/권한 관리
- 거래상태 "정상/주의"(납기지연 등) 세분화 — 지금은 SETTLED/FAILED뿐
- VPC 3개 등 네트워크 구성 실제 구현 — 도식(발표자료)용으로만 존재

## 5. 알려진 함정 (재발 방지용)

| 상황 | 원인 | 대응 |
|---|---|---|
| `sqlalchemy.exc.OperationalError: table ... has no column named ...` | `schemas.py`/`store.py`에 필드를 추가했는데 기존 `data/mmvp.db`는 옛 스키마 그대로 남아있음. `create_all()`은 없는 테이블만 만들지, 기존 테이블에 컬럼을 추가해주지 않음 | **스키마 변경할 때마다 `data/` 폴더 통째로 삭제 후 서버 재기동.** 지금 개발 단계에선 이게 제일 간단한 대응 (Alembic 같은 마이그레이션 도구는 이 스코프엔 과함)<br>**Odoo 연동에서 컬럼 4개가 늘었습니다** — `seller_catalog.min_qty`, `deals.po_id/po_name/po_error`. 기존 `data/`를 갖고 있다면 반드시 지우고 재기동하세요 |
| 목업 1번 화면 "등록"이 409 | `CATALOG_SOURCE=odoo` 에서는 카탈로그의 주인이 Odoo라 이 서비스로는 못 쓴다 | 정상 동작입니다. 공급처·단가는 Odoo에서 등록하세요: Purchase > Products > 해당 품목 > Purchase 탭 |
| Odoo 발주서 링크가 다른 기기에서 안 열림 | 링크 주소가 서버 입장의 `localhost`로 만들어짐 | `.env`의 `ODOO_PUBLIC_URL`에 **브라우저가 닿는 주소**를 넣으세요 |
| `pkill -f "uvicorn app.main:app"` 로 재기동했더니 새 서버도 죽음 | pkill 패턴이 **자기 명령줄까지** 매칭해 부모 셸을 죽임 | PID를 집어서 죽이세요: `kill $(pgrep -f "[u]vicorn app.main")` |
| `ModuleNotFoundError: No module named 'app'` | `app/` 폴더 없이 `.py` 파일들이 프로젝트 루트에 바로 풀려있음 | `uvicorn app.main:app`은 "현재 폴더에 `app` 패키지가 있다"는 전제. 폴더 구조 재확인(§7 폴더구조 문서 참고) |
| PowerShell에서 `export OPENAI_API_KEY=...` 안 먹힘 | `export`는 bash 문법, PowerShell은 `$env:`가 필요 | `.env` 파일 사용 (`.env.example` 복사 후 값 채우기) — OS/셸 무관하게 동작 |
| 목업이 AWS에서 API 호출 실패 | 예전 버전은 `const API = "http://127.0.0.1:8000/api"`로 하드코딩되어 있었음 | 이미 수정됨(`const API = "/api"` 상대경로) — `static/index.html`이 최신본인지 확인 |

## 7. 실행 방법 요약

```bash
pip install -r requirements.txt
copy env.example .env      # Windows / cp env.example .env (Mac·Linux)
# .env 열어서 값 채우기:
#   NEGOTIATOR_MODE  rule(기본) / llm(OPENAI_API_KEY 필요, 미지정 시 gpt-4o-mini)
#   CATALOG_SOURCE   sqlite(기본) / odoo
uvicorn app.main:app --reload --port 8000
# 브라우저로 http://127.0.0.1:8000/ 접속 (목업+API 같은 포트에서 서빙됨)
```

`CATALOG_SOURCE=odoo` 로 쓰려면 Odoo를 먼저 띄우고, `.env`의 `ODOO_*` 를 채운 뒤
데모 데이터를 한 번 넣습니다 (멱등이라 여러 번 돌려도 안전):

```bash
python scripts/seed_odoo_demo.py
```

스키마(필드) 변경 후에는 반드시 `data/` 폴더 삭제 후 재기동.
