# `data/nexar_snapshot.json` 구조

4.2MB 한 덩어리라 에디터로 열어 훑기 어렵습니다. 이 문서는 **무엇이 어디에 들어
있는지**와 **어떤 필드가 얼마나 비어 있는지**를 정리합니다. 아래 채움률은 실제
스냅샷(2026-09-04 조회, 28품목)을 세어서 적은 값입니다.

관련 문서와 역할이 다릅니다.

| 어디 | 무엇 |
|---|---|
| 이 문서 | 파일 안에 무엇이 들어 있는가 |
| `README.md` | 무엇이 실데이터이고 무엇이 합성인가, 어떻게 켜는가 |
| `app/snapshot_catalog.py` | 이 값들을 협상 카탈로그로 어떻게 해석하는가 |
| 파일 안의 `provenance.query` | **필드의 정본** — 무엇을 물어봤는지가 그대로 들어 있다 |

---

## 파일 한눈에

```jsonc
{
  "provenance": {          // 이 파일이 어떻게 만들어졌는가
    "endpoint":  "https://api.nexar.com/graphql",
    "fetched_at": "2026-09-04T17:11:06+0900",
    "query":     "query($queries: ...) { supMultiMatch ... }",  // 보낸 쿼리 전문
    "variables": { "queries": [{ "mpn": "...", "limit": 1, "reference": "..." }] },
    "moq_field": "moq",    // 로더가 MOQ를 어느 키에서 읽을지
    "note":      "API 응답 원본. 합성값 없음."
  },
  "response": { "supMultiMatch": [ /* 조회한 MPN마다 1건 */ ] }
}
```

**`query`를 함께 남기는 이유** — GraphQL 응답은 보낸 쿼리에 대한 투영입니다.
쿼리를 모르면 어떤 필드가 *없는* 것인지 *안 물어본* 것인지 구분할 수 없습니다.

## 중첩

```
response.supMultiMatch[]        28건   조회한 MPN 하나당 1건
└── parts[]                     28개   limit:1 이라 MPN당 1개만 (hits 는 더 클 수 있다)
    ├── specs[]                        부품 사양 (평균 40여 개)
    └── sellers[]             1,150개   같은 판매자가 여러 부품에 반복 등장
        └── offers[]          1,461건   한 판매자가 포장 단위별로 여러 개를 낼 수 있다
            └── prices[]      5,744개   수량구간별 단가
```

## 계층별 필드

### `supMultiMatch[]` — 조회 1건

| 필드 | 채움률 | 뜻 |
|---|---|---|
| `reference` | 100% | 우리가 넣은 MPN 문자열. 정규화 전 값이라 `parts[].mpn` 과 다를 수 있다 |
| `hits` | 100% | 매칭된 부품 총 개수. `limit:1` 이라 `parts` 에는 1개만 담긴다 |
| `parts[]` | 100% | 아래 |

### `parts[]` — 부품

| 필드 | 채움률 | 예 / 뜻 |
|---|---|---|
| `mpn` | 100% | `LM2596S-5.0/NOPB` — 정규화된 제조사 품번 |
| `shortDescription` | 100% | 한 줄 사양. 로더가 `spec` 으로 쓴다 |
| `manufacturer.name` | 100% | `Texas Instruments` |
| `category.name` / `.path` | 100% | `Voltage Regulators - Switching` |
| `totalAvail` / `avgAvail` | 100% | 전 유통사 재고 합 / 평균 |
| `medianPrice1000` | 100% | 1000개 기준 시장가. **협상 근거로 쓸 만한 기준선** |
| `octopartUrl` | 100% | 출처 링크 |
| `bestDatasheet.url` | 100% | 데이터시트 |
| `specs[]` | 100% | `{attribute:{name,shortname,group}, value, displayValue, units}` |
| `genericMpn` | 100% | `LM2596` — 시리즈 |
| `estimatedFactoryLeadDays` | 96% | 부품 단위 추정 리드타임 |
| `akaMpns[]` | 93% | 같은 부품의 다른 표기 |
| `id` / `name` | 100% | Octopart 내부 ID / 표시명 |

### `sellers[]` — 판매자

| 필드 | 채움률 | 뜻 |
|---|---|---|
| `company` | 100% | `{id, name, homepageUrl, isVerified}` |
| `isAuthorized` | 100% | **인가 유통사 여부.** 로더의 기본 필터가 쓰는 유일한 기준 |
| `isBroker` | 100% | 이 데이터에서는 **전부 `false`** — 판별에 쓸 수 없다 |
| `country` | 100% | `US`, `HK`, `CN` … |
| `isRfq` | 100% | 견적 필요 여부 |

### `offers[]` — 오퍼

**여기가 결측이 많은 계층입니다.** 로더가 정규화하는 이유가 이 표에 있습니다.

| 필드 | 채움률 | 뜻 |
|---|---|---|
| `inventoryLevel` | 100% | 재고. 0인 경우가 흔하다(값 자체는 항상 있다) |
| `sku` | 100% | 유통사 품번 — 발주 단계에서 필요 |
| `updated` | 100% | 이 오퍼가 갱신된 시각 |
| `clickUrl` | 100% | 유통사 페이지 링크 |
| `isCustomPricing` | 100% | 견적 전용이면 표시가가 의미를 잃는다 |
| `eligibleRegion` | 11% | 지역 제한. 89%는 빈 문자열이고, 값이 있어도 표기가 제각각이다 (`US` · `AMER` · `19` · `14`) |
| `prices[]` | **89%** | 11%는 가격이 없다. 로더가 후보에서 제외한다 |
| `moq` | **59%** | **41%가 없다.** 스키마가 `int` 라 로더가 `0`(제약 없음)으로 정규화 |
| `orderMultiple` | **24%** | 주문 배수 제약. **아직 안 쓴다** |
| `packaging` | 22% | `Tube`, `Cut Tape` … |
| `factoryLeadDays` | **16%** | 공장 재생산 시간. **재고 출하 납기가 아니다** |
| `onOrderQuantity` | 3% | 입고 예정 수량 |
| `factoryPackQuantity` | 2% | 공장 포장 단위 |
| `multipackQuantity` | 1% | |

### `prices[]` — 수량구간

| 필드 | 채움률 | 뜻 |
|---|---|---|
| `quantity` | 100% | 이 단가를 받기 시작하는 수량 |
| `price` | 100% | 원 통화 단가 (실수) |
| `currency` | 100% | USD가 대부분. EUR·HKD·CNY·JPY·GBP도 있다 |
| `convertedPrice` | 100% | **API가 환산한 KRW 단가** — 로더가 이 값을 쓴다 |
| `convertedCurrency` | 100% | `KRW` |
| `conversionRate` | 100% | 적용된 환율. 원 통화마다 다르다 |

## 걸려 넘어지기 쉬운 곳

1. **`moq` 가 41% 없다.** `None` 을 `SellerRegister.min_qty`(int)에 그대로 넘기면
   pydantic 검증에서 터집니다. 로더가 `0` 으로 정규화합니다.
2. **`factoryLeadDays` 는 재고 출하 납기가 아닙니다.** 재고와 배타적이지도 않아서,
   재고를 가진 오퍼 107건이 이 값을 함께 갖습니다. 그대로 납기로 쓰면 재고 8,324개를
   가진 DigiKey 가 "납기초과 280일"로 탈락합니다.
3. **`isBroker` 로는 못 거릅니다.** 전부 `false` 입니다. 인가 여부는 `isAuthorized` 뿐입니다.
4. **같은 판매자가 한 부품에 여러 오퍼를 냅니다.** 포장 단위 차이입니다.
   로더는 최저가만 남깁니다 — 협상 상대가 중복으로 등장하면 로그가 읽히지 않습니다.
5. **`reference` 와 `mpn` 이 다를 수 있습니다.** `EEU-FR1V101` 로 조회하면
   `EEUFR1V101` 로 정규화되어 돌아옵니다.
6. **`hits` 가 1보다 커도 `parts` 는 1개입니다.** 쿼리에서 `limit: 1` 을 줬기 때문입니다.

## 아직 안 쓰는 필드

받아두었지만 현재 로더가 읽지 않습니다. 한도는 조회한 파트 수로만 깎이고 필드
수로는 깎이지 않아서, 나중에 쓸 법한 것을 함께 받아둔 것입니다.

`orderMultiple` · `onOrderQuantity` · `factoryPackQuantity` · `multipackQuantity` ·
`isCustomPricing` · `sku` · `packaging` · `updated` · `specs` · `medianPrice1000` ·
`akaMpns` · `genericMpn` · `category` · `bestDatasheet` · `octopartUrl` ·
`totalAvail` · `avgAvail` · `estimatedFactoryLeadDays` · `country` · `isRfq` ·
`company.homepageUrl` · `company.isVerified`

## 작업지시서와 달라진 점

`docs/카탈로그-스냅샷-작업지시.md` 는 스냅샷이 `rows` 배열이고 각 행에
`seller_id` · `offer_price` · `floor_price` · `_synthetic_fields` 를 갖는 형태를
전제합니다. **현재 파일은 그 형태가 아닙니다.**

조회 한도가 파트 수로 깎여 원본을 다시 뜨는 비용이 크다는 점 때문에, 되돌릴 수
없는 원본은 손대지 않고 남기고 해석은 읽는 시점으로 미루는 쪽으로 바꿨습니다.
그 결과 `floor_price` 합성·통화 환산·수량구간 선택·결측 정규화가 전부
`app/snapshot_catalog.py` 로 옮겨갔고, 스냅샷 파일에는 합성값이 하나도 없습니다.
가정이 바뀌어도 로더만 고치면 되고 재조회가 필요 없습니다.

지시서의 나머지(변경 지점, 병렬 작업자와의 경계, 함정 목록)는 그대로 유효합니다.
