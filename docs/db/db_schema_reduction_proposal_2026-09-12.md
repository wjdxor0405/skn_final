# DB 스키마 축소 제안서

작성일: 2026-09-12
근거: 멘토 리뷰 세션 원문(`db관련 대화 원문.txt`) + 현재 develop 코드 사용 현황 감사
기준 문서: [table_spec.md](table_spec.md) v4 (58개 테이블 · 12개 스키마)

## 0. 배경과 원칙

멘토 피드백 핵심 3가지:

1. **12개 스키마 · 58개 테이블은 이 프로젝트 규모·일정 대비 과설계.** 1NF/2NF/BCNF 교과서식 정규화는 이상적이지만, 실무에서는 조인 비용·유지보수 부담 때문에 이 정도로 안 쪼갠다.
2. **벡터(RAG 임베딩)를 RDB에 넣는 설계는 틀렸다.** ⚠️ **[2026-09-12 방향 확정]** 현재 develop 코드(`src/repo/rag_repo.py`)는 pgvector(PostgreSQL 확장)로 같은 DB 안에 벡터를 저장하고 있어서, 엄밀히는 "별도 벡터DB와 중복 저장"은 아닙니다. 다만 **RAG 쪽 설계가 아직 팀에서 최종 정리된 게 없기 때문에, 이 문서에서는 "RAG는 별도 벡터DB를 쓴다"고 가정하고 정리**합니다. 이건 현재 코드 상태에 대한 사실 진술이 아니라, **앞으로 그렇게 가기로 한 하나의 방향(가정)**이며 담당4 확인이 필요합니다. (이전에 "pgvector=PostgreSQL 확장이라 문제없다"고 정정했던 내용은 사실관계로는 맞지만, 팀이 "그래도 별도 벡터DB로 가겠다"고 방향을 정한다면 이 문서는 그 방향을 따릅니다.)
3. **이 프로젝트엔 확정된 "다음 버전(후반)"이 없다.** 그러니 "나중에 쓸 수도 있으니 스키마는 만들어 두고 비워만 둔다"는 접근이 틀렸다. **이번에 실제로 쓸 것과, 안 쓸 것 두 가지로만 나누고, 안 쓸 것은 지금 스키마에서 아예 뺀다.**

이 문서는 위 원칙을 스키마별로 적용한 결과다. 각 항목은 출처를 표시한다:

- **[확정]** 멘토 리뷰 세션에서 실제로 합의된 것 (원문 타임스탬프 인용)
- **[제안]** 이 문서를 준비하며 제가 추가로 드리는 안
- **[확인 필요]** 세션에서도 결론이 안 나거나, 아예 다루지 않은 항목

> **[2026-09-12] 팀 확인 완료**: `rag`를 뺀 나머지 스키마(config·identity·shared·catalog·assets·community·evidence·engine·planning·notification·dataset)는 아래 내용대로 **팀 확인을 받아 확정**되었습니다. 이전에 [제안]/[확인 필요]로 표시했던 항목들도 이 확정에 포함됩니다 — 표시는 근거 추적용으로 남겨둡니다. **`rag`만 별도 벡터DB 사용 여부가 아직 미정이라 보류** 상태입니다.

### rag (6 → 0, 스키마 전체 삭제) — [가정] 별도 벡터DB 사용

> **원문 근거 (세션 도입부, 66:37-67:40)** — 이 논의는 애초에 여기서 시작됩니다:
> ```
> [67:23] 화자1: 지금 아이디IV만 설계하신 거예요?
> [67:27] 화자1: 벡터 DB 포함해서 설계한 거예요?
> [67:31] 화자2: 아니요. 이건 지금 RDB만 먼저 설계 자료로 보여드리고
> [67:34] 화자1: RDB에 저 RAG가 왜 들어가요?
> [67:40] 화자2: 배종료 혹시 답변해 주실 수 있으실까요?
> ```
> 즉 팀은 애초에 **RDB만 먼저 설계해서 보여준 것**이고, 벡터DB는 별도로 설계한 적이 없습니다(화자2가 직접 인정). 멘토님의 첫 반응이 "RDB에 왜 RAG가 들어가 있냐"는 반문이었다는 게 이 논의의 출발점입니다. 뒤이어 나온 "그냥 없는 게 맞아요..." (68:53, 아래 인용)는 이 반문에 대한 상세 설명입니다.

> **사실관계 참고**: 지금 develop 코드는 pgvector(PostgreSQL 확장)로 같은 DB에 저장하고 있어서, "별도 벡터DB가 있어서 중복"이라는 게 현재 코드 기준 사실은 아닙니다(`CREATE EXTENSION vector`, `rag.chunk_embedding.embedding vector(1024)` — 전부 같은 데이터베이스). 다만 위 원문처럼 **애초에 팀이 벡터DB를 별도로 설계한 적이 없고 RDB만 먼저 만들어서 보여준 상황**이었고, **RAG 아키텍처가 아직 팀에서 최종 확정되지 않았기 때문에, "RAG는 별도 벡터DB를 쓴다"는 방향으로 가정하고 이 문서를 정리**합니다. 이 가정이 맞다면 아래처럼 정리됩니다.

| 테이블 | 처리 | 근거 |
|---|---|---|
| `chunk_embedding`, `document_chunk`, `embedding_profile`, `ingestion_job`, `retrieval_run`, `retrieval_hit` | **RDB에서 전부 제거** | [가정] RAG가 별도 벡터DB를 쓴다면, 청크 텍스트·임베딩·적재 이력·검색 로그까지 그 벡터DB(또는 벡터DB가 제공하는 메타데이터 저장 기능) 쪽에서 전담. RDB는 이 데이터를 아예 안 가짐 |

**재설계 방향**: RAG 파이프라인이 만들어낸 청크·벡터·검색 이력은 전부 벡터DB에서 관리하고, RDB에는 그 결과로 나온 "검증된 결론"만 남습니다 — 예를 들어 추천에 실제로 채택된 근거는 `evidence.evidence`에, 검증된 스펙은 `catalog.product_fact`에.

⚠️ **현재 코드와의 갭**: `src/repo/rag_repo.py`(담당4, +520줄)는 지금 이 6개 테이블을 SQL JOIN으로 직접 쓰고 있습니다. 이 가정대로 가면 그 구현을 벡터DB 클라이언트 호출로 다시 짜야 합니다 — **이 문서에서 되돌리기가 가장 비싼 항목**이니, 실제로 이 방향으로 갈지 담당4와 먼저 확정하고 진행하세요.

**더 줄이고 싶다면(선택 사항, 신중 권장)**: `plan`+`plan_revision`을 합치면 4개까지 가능하지만, 이러면 "재탐색 라운드마다 새 버전", "확정 시점 스냅샷 보존" 같은 버전 관리 기능 자체를 포기해야 합니다. 지난번 "보수적으로 가고 싶다"는 방향과 맞지 않아서 **이 문서에서는 포함하지 않았습니다** — 필요하면 담당2와 별도로 논의하세요.

## 2-1. 되돌리기 난이도 — 실제로는 이 순서로 진행 권장

forward-only 마이그레이션 구조라 "테이블을 다시 만드는 SQL"은 항상 쉽습니다. 진짜 비용은 **이미 그 모양에 맞춰 짜인 코드·데이터를 다시 풀어야 하는 것**입니다. 이 기준으로 난이도를 나누면:

| 항목 | 난이도 | 이유 |
|---|---|---|
| `notification` 3개 삭제 | 쉬움 | 코드 미사용(감사 완료) · 데이터 없음. 필요시 옛 `0001_tables.sql`의 CREATE TABLE 그대로 재사용 가능 |
| `dataset` 4개 삭제(파일 이전) | 쉬움 | 동일 — 코드 미사용, 데이터 없음 |
| `config`·`identity` 병합 | 쉬움 | `UserRepo`가 빈 껍데기(`pass`)라 의존 코드 없음 |
| `planning` 8→5 | 쉬움 | 관련 기능 전부 구현 전, 코드 의존 없음 — 지금이 가장 싸게 바꿀 수 있는 시점 |
| `community`·`evidence` 병합 | 쉬움~중간 | 대부분 스텁 단계. 담당5가 실로직을 이미 짠 부분이 있다면 그만큼 비용 증가 |
| `shared.unit` 흡수 | 쉬움 | 사용처가 카탈로그 옵션 하나뿐 |
| `catalog`·`engine` 병합 | 쉬움 | 코드 미사용, 팀 확인 완료 |
| `plan`+`plan_revision` 병합(선택, 미포함) | 중간~어려움 | 버전 이력 자체를 포기하는 결정이라, 나중에 "역시 필요했다"가 나오면 데이터 마이그레이션까지 필요 |
| **`rag` 스키마 전체 삭제 (별도 벡터DB 가정)** | **매우 어려움** | 담당4가 이미 `rag_repo.py` 500여 줄을 이 6개 테이블 기준(pgvector)으로 구현. 별도 벡터DB로 가면 그 구현을 전부 다시 짜야 하고, 나중에 "역시 pgvector가 낫다"로 되돌리면 또 한 번 다시 짜야 함 — 이 문서에서 유일하게 "이미 짜인 코드를 버리는" 항목 |

### 진행 순서

**지금 바로 진행 (58 → 35, 팀 확인 완료)**: `notification`·`dataset`·`shared` 스키마 삭제, `config`·`identity`·`catalog`·`assets`·`community`·`evidence`·`engine`·`planning` 병합.

**담당4 명시적 합의 후에만 (35 → 29)**: `rag` 스키마 전체 삭제. 합의되더라도 한 번에 지우지 말고, 별도 벡터DB 경로를 먼저 만들어 검증한 다음 단계적으로 RDB 쪽을 제거하는 걸 권합니다.

## 3. 남은 확인 항목 — `rag` 하나뿐

**`rag` 스키마 전체 삭제(별도 벡터DB 가정) 여부.** 현재 코드는 pgvector로 같은 DB에 저장 중이라, 이 문서의 가정과 실제 구현이 다릅니다. 담당4에게 "RAG를 정말 별도 벡터DB로 갈 건지, 아니면 지금처럼 pgvector로 같은 DB에 둘 건지"부터 확정받아야 최종 숫자(29 vs 35)가 정해집니다. 그 외 항목은 전부 팀 확인을 받아 확정되었습니다.

## 4. 진행 방식

DB 마이그레이션 실제 반영은 이 문서 확정 내용을 바탕으로 진행합니다. `rag`를 뺀 나머지(58 → 35, `notification`·`dataset`·`shared` 스키마 삭제 + `config`·`identity`·`catalog`·`assets`·`community`·`evidence`·`engine`·`planning` 병합)는 바로 마이그레이션 작성에 들어가도 됩니다. **`rag` 스키마 삭제는 담당4의 기존 구현(`src/repo/rag_repo.py`, +520줄)을 통째로 무효화하는 가정**이라, 담당4의 명시적 동의를 받은 뒤 별도로 반영합니다.
