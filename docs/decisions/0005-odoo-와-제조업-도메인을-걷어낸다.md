# 0005. Odoo 연동과 제조업 도메인을 걷어낸다

- 날짜: 2026-09-07
- 상태: 결정됨
- 관련: [`wiki_대조_20260907.md`](../wiki_대조_20260907.md),
  커밋 `be01e3f`(기본값 전환) · `7228944`(Odoo 제거) · `c134af2`(BOM 제거)

## 맥락

이 저장소는 세 축 위에 서 있었다 — **제조업 도메인 · Odoo(CRM/ERP) · B2B 협상.**
9/5~9/6 회의 7건에서 앞의 두 축이 무너졌다.

**제조업.** 팀원의 가족(제조업 현업)에게 자문한 결과가 종합적으로 부정이었다.
양산품은 스펙이 고정이고 수량이 안정적이라 "전화 한 통이면 되고", 개발품은
소재·세부 요구사항이 매번 바뀌어 "경험적·감각적 판단이라 AI가 대체하기 어렵다".
결정타는 견적이었다 — **인건비·유지보수비를 반영하지 않으면 손해가 나는데 그건
데이터로 산출할 수 없다.** 책임질 사람이 판단해야 하는 영역이다.

**CRM.** 대기업은 자체 시스템이 충분해 외부 CRM이 필요 없고, 중소 하청업체는
CRM을 아예 쓰지 않는다. 9/6 회의의 최종 정리 첫 줄이 "CRM은 버리고 마켓플레이스
컨셉으로 확정"이었고, 도메인도 "인건비 부담이 적은 업종(직거래 등)"으로 옮겼다.

살아남은 축은 **협상**이고, 새 도메인에 맞는 카탈로그가 이미 있었다 —
`snapshot` 모드의 전자부품 유통 실데이터 28품목·1,039행이다.

## 결정

**세 커밋으로 나눠서, 지우기 전에 기본값부터 바꾼다.**

1. `CATALOG_SOURCE` 기본값을 `sqlite` → `snapshot` (`be01e3f`)
2. Odoo 카탈로그 출처를 제거 (`7228944`) — 약 1,167줄
3. 제조(BOM) 경로를 제거 (`c134af2`) — `feasibility.py` 258 → 199줄

순서가 중요하다. 1번만으로 이미 Odoo 경로가 메인에서 빠지므로, **코드를 지우기
전에 "기본 경로가 실제로 도는가"를 확인할 수 있다.** 되돌리기도 커밋 하나다.

2와 3을 나눈 이유는 성격이 달라서다. 2는 **출처 교체**(Odoo → 스냅샷), 3은
**도메인 축소**(만들어 파는 것 → 사다 파는 것)다. 섞으면 나중에 제조 경로만
되살리고 싶을 때 고를 수 없다.

## 남긴 것과 그 이유

| 남긴 것 | 이유 |
|---|---|
| 협상 일체(`negotiate`·`agents`·`llm_agents`·`audit`) | 협상은 폐기되지 않았다. 그리고 협상이 메인 테마인지가 아직 안 갈렸다(아래) |
| 정보 비대칭(`5462e43`·`1ade8d9`) | 멘토 지적 "바이어가 먼저 상한가를 부르는 건 실무와 안 맞다"에 대한 답이 이미 들어가 있다 |
| `sqlite` 모드 | 셀러가 카탈로그를 직접 올리는 경로다. 9/5 회의의 "판매자가 AI가 읽을 카탈로그를 등록한다"가 정확히 이것이라 새 방향에서 오히려 필요하다 |
| `data/nexar_snapshot.json` | 무료 플랜 한도는 조회한 파트 수로 차감된다. 이미 태웠고 **다시 못 뜬다.** 멘토도 "BM이 정해질 때까지 데이터 수집을 멈추라"고 했다 |
| `on_hand` 필드(상수 0) | 실제 재고 출처가 생기면 `_product()` 한 곳만 바뀐다 |

## 대가

- **"에이전트가 언제 나서지 않는가"를 잃었다.** `intake.py`의 표준계약 분기가
  이 프로젝트에서 가장 값나가는 장면이었다. 멘토가 9/5부터 반복한 지적("AI가
  있으나 마나 한 프로세스 API 수준")에 대한 답이었고, 해커톤 트랙 적합성의
  근거이기도 했다(`해커톤_요건_대조.md` §5가 이걸 "Potential Impact에서 가장 강한
  자산"으로 꼽았다). Odoo에 묶인 것은 **기준값의 저장 위치뿐**이라 옮겨 심을 수
  있지만, 어디로 옮길지가 아직 안 갈린 쟁점에 걸려 있다
- **Odoo 연동 자체가 자산이었다.** JSON-RPC 클라이언트 363줄은 표준 라이브러리만
  쓰고 XML-RPC의 `None` 마샬링 함정까지 피해 놓은 코드다. 다시 필요해지면
  `git revert 7228944`
- **제조업 시연 시나리오 전체를 잃었다.** BOM 전개로 "GPU 재고 10장뿐이라 90장
  부족, 조달 7일 + 제조 5일 + 생산 10일 = 22일 필요"라고 답하던 장면은 유통
  데이터로 재현되지 않는다. 남은 것은 조달 납기 한 항이다

## 검토했다가 안 간 길

- **`main` 에서 새 브랜치를 따고 다시 짜기.** 이 포크는 아무것도 main에 병합된
  적이 없어서 `main` 에는 `README.md` 한 파일뿐이다. "새로 시작"이 아니라
  **107,328줄 삭제**이고, 다시 못 뜨는 스냅샷 데이터와 문서 8개가 같이 날아간다.
  게다가 실제로 죽은 코드는 전체의 17%였다
- **지우지 않고 환경변수 기본값만 바꾸기.** 처음에 권했던 안이다. 이틀 사이
  방향이 세 번 바뀌었으니(멘토도 "오늘이 벌써 세 번째 점프"라고 짚었다) 되돌릴
  길을 남기는 값이 싸다고 봤다. **팀이 갈아엎기로 정해서 지우는 쪽으로 갔고,
  대신 커밋을 잘게 나눠 `revert` 단위를 남겼다** — 되돌릴 길은 브랜치가 아니라
  커밋 경계로 지킨다
- **`intake.py`의 기준값만 SQLite로 옮겨 표준계약 분기를 살리기.** 기술적으로는
  반나절이다. 안 한 이유는 **협상이 메인 테마인지가 안 갈렸기 때문**이다. 팀은
  9/6 22시에 "마켓플레이스 B2B 협상을 메인으로 유지"한다고 설명했는데 멘토의
  수렴 도식(추천 시스템 / 합리적 구매 클린징)에는 협상 노드가 없다. 그게 정해지기
  전에 옮겨 심으면 두 번 옮기게 된다

## 확인한 것 (계획과 달랐던 부분)

**DB는 지우지 않아도 된다.** 계획 단계에서는 `deals` 컬럼 3개가 빠지므로
`data/` 삭제 후 재기동이 필요하다고 봤다. `프로젝트_현황.md` §5의 그 함정이
떠올랐기 때문이다. 실제로 재보니 아니었다 — `po_id`/`po_name`/`po_error` 는
nullable이라 모델 선언에서 빠져도 기존 테이블에 남은 채 무시된다. 기존 72행이
든 DB로 새 거래 등록·승인·리포트 생성까지 왕복 확인했다.

**컬럼 추가와 제거는 방향이 다르다.** `create_all()` 은 없는 테이블만 만들지
기존 테이블에 컬럼을 **추가**해 주지 않아서, 추가는 반드시 깨진다. 제거는
남은 컬럼이 nullable이기만 하면 조용히 넘어간다. §5의 함정 문구는 추가에
대한 것이었고, 제거까지 같은 대응이 필요한 것처럼 읽혔다.
