# 0002. 스냅샷은 API 응답 원본을 보존하고, 해석은 읽는 시점에 한다

- 날짜: 2026-09-05
- 상태: 결정됨
- 관련: `docs/카탈로그-스냅샷-작업지시.md`, `docs/스냅샷-데이터-구조.md`,
  `app/snapshot_catalog.py`, `scripts/nexar_snapshot.py`

## 맥락

`CATALOG_SOURCE=snapshot` 은 Nexar(Octopart) API 응답을 커밋해서 읽는다. 심사위원이
API 키 없이 실행할 수 있어야 하기 때문이다.

작업지시서가 함께 준 `scripts/nexar_snapshot.py` 초안은 조회하는 시점에 변환까지
했다. 응답을 `rows` 배열로 평탄화하고, 각 행에 `seller_id` · `offer_price` ·
합성한 `floor_price` · `_synthetic_fields` 를 담는 형태였다.

여기에 비용 비대칭이 하나 있다.

- **원본은 사실상 다시 못 뜬다.** 무료 플랜의 한도가 조회한 '파트 수'로 깎인다.
  이번 조회로 28파트를 썼다. 지시서도 "한 번 제대로 돌리고 결과를 커밋하라"고 못박았다
- **변환은 언제든 다시 한다.** 파일을 다시 읽고 계산하는 데 몇 밀리초다

변환을 조회 시점에 구우면 이 비대칭에서 잘못된 쪽을 고정하게 된다. 실제로 초안대로
갔으면 다음 것들이 전부 재조회 사유가 됐다.

- `SellerRegister.offer_price` 가 `int` 인데 전자부품 단가는 대부분 1달러 미만의
  실수다. 그대로 넣으면 pydantic 검증에서 터진다(`0.0234` → ValidationError).
  환산 단위를 정해야 하는데, 그 판단이 파일에 굳는다
- 지시서는 `SNAPSHOT_FLOOR_RATIO` 환경변수를 두라고 하면서 같은 값을 파일에
  구우라고 했다. **파일에 이미 `floor_price` 가 있으면 그 환경변수는 아무 일도 안 한다**
- 초안은 가격 없는 오퍼를 버렸다(`if not tiers: continue`). 재고·납기·유통사 정보는
  남을 가치가 있는데 복구가 불가능해진다

## 결정

**`data/nexar_snapshot.json` 에는 API 응답 원본만 넣는다. 합성값을 하나도 굽지 않는다.**

옆에 조회 이력(`provenance`)을 붙인다 — 엔드포인트 · 시각 · **보낸 쿼리 전문** ·
변수 · MOQ 필드명. 쿼리를 함께 남기는 이유는 GraphQL 응답이 보낸 쿼리에 대한
투영이라, 쿼리를 모르면 어떤 필드가 *없는* 것인지 *안 물어본* 것인지 구분할 수 없기
때문이다.

**해석은 전부 `app/snapshot_catalog.py` 가 읽는 시점에 한다.** 통화 환산, 수량구간
선택, `floor_price` 합성, 결측 정규화, 판매자 필터가 여기 있다. 가정이 바뀌면
이 파일만 고치고 서버를 다시 띄우면 되고, 재조회가 필요 없다.

**필드는 넉넉히 받는다.** 한도는 파트 수로만 깎이고 필드 수로는 깎이지 않는다.
원본을 보존해도 *안 물어본 필드는 없으므로*, introspection 으로 존재를 확인한 것을
이번 한 번에 같이 받았다(`scripts/nexar_snapshot.py` 의 `EXTRA_*_FIELDS`).

## 이 결정으로 실제로 달라진 것

조회 뒤에 드러난 문제 넷을 **재조회 없이** 고쳤다. 초안 구조였으면 넷 다 재조회였다.

1. `supMultiMatch` 가 `currency` 인자를 받는다. 응답에 API가 계산한 환산값이 실린다.
   실측 환율은 USD 1,351.30 이었고 우리 가정치 1,400 과 3.4% 차이가 났다.
   **가정을 실데이터로 대체**했다 — 지금 1,039행 전부 API 환산값을 쓴다
2. 원 통화가 하나가 아니었다(USD · EUR · HKD · CNY · JPY · GBP). 단일 환율 가정이
   애초에 틀렸다
3. `factoryLeadDays` 를 납기로 쓰고 있었는데 이건 공장 재생산 시간이다. 재고와
   배타적이지도 않아서(오퍼 107건이 둘 다 가짐) 재고 8,324개를 가진 DigiKey 가
   "납기초과 280일"로 탈락하고 있었다
4. 비인가 유통사가 협상을 지배하는 문제 → ADR 0003

## 대가

- **파일이 크다.** 4.2MB(git 저장 0.66MB). 변환된 형태였으면 훨씬 작다.
  merge 전까지 upstream clone 크기에는 영향이 없고, merge 후에는 영구적이다
- **로더가 무겁다.** 결측 정규화·중복 제거·구간 선택이 전부 읽는 시점에 돈다.
  프로세스당 1회 캐시로 덮었지만 공짜는 아니다
- **파일만 봐서는 카탈로그를 알 수 없다.** 원본은 중첩이 5단이라
  `snapshot_catalog.diagnostics()` 를 거쳐야 "몇 행이 남고 무엇이 왜 빠졌는지"가 보인다.
  `docs/스냅샷-데이터-구조.md` 가 이 간극을 메우려는 문서다
- **작업지시서와 어긋난다.** 지시서는 `rows` · `_synthetic_fields` 형태를 전제한다.
  그대로 믿고 파일을 열면 맞지 않는다(구조 문서 마지막 절에 명시)

## 검토했다가 안 간 길

- **초안대로 조회 시점 변환** — 위 넷이 전부 재조회 사유가 된다
- **원본과 변환본을 둘 다 커밋** — 변환본이 로더와 어긋나 낡는다. 진실이 두 곳에
  있으면 어느 쪽이 맞는지 물어야 한다
- **조회 단계에서 `requireAuthorizedSellers` 로 거르기** — 파일이 작아지지만
  원본을 손상시킨다. 걸러진 판매자는 영영 없다. 필터는 읽는 시점에 둔다(ADR 0003)
