# 작업 지시 — CATALOG_SOURCE=snapshot 추가

담당: (작성자 본인) / 병렬 작업자: Strands 이식 담당
브랜치: `feat/snapshot-catalog` (`feat/odoo-integration`에서 분기)

---

## 배경

셀러 카탈로그가 지금은 `sqlite`(화면 등록)와 `odoo`(공급처 단가표) 둘뿐이다.
둘 다 데모용 가상 데이터라서, 협상 화면에 뜨는 단가·납기·MOQ가 전부 지어낸 값이다.

Nexar(Octopart) API에서 실제 전자부품 유통 데이터를 받아 세 번째 출처로 붙인다.
한 부품에 **여러 유통사의 오퍼**가 붙어 있어서, 복수 후보 비교라는 이 프로젝트의
핵심 시연 장면이 실데이터로 성립한다.

심사위원은 API 키 없이 실행할 수 있어야 하므로 **라이브 호출이 아니라 JSON 스냅샷을
커밋해서 읽는 방식**으로 간다. 라이브 조회는 스냅샷을 다시 뜰 때만 쓴다.

---

## 하지 말 것 (다른 사람 영역)

Strands 이식 담당이 아래 파일을 동시에 고치고 있다. **손대지 말 것.**

- `app/llm_agents.py`
- `app/negotiate.py`
- `app/agents.py`, `app/audit.py`

`env.example` / `requirements.txt` / `pyproject.toml` / `README.md`는 **양쪽이 다 건드린다.**
추가만 하고 기존 줄은 재배열하지 말 것. 충돌이 나도 3-way merge로 쉽게 풀리게 둔다.

## 목표

`CATALOG_SOURCE=snapshot`으로 앱이 뜨고, 협상이 실데이터 카탈로그로 돌아간다.
`negotiate.py`·`report.py`는 출처를 몰라야 한다 — 기존 설계 원칙 그대로.

## 변경 지점 (정확히 여기만)

### 신규
- `scripts/nexar_snapshot.py` — 이미 작성됨. 그대로 넣는다
- `data/nexar_snapshot.json` — 스크립트 산출물. **커밋한다**
- `app/snapshot_catalog.py` — 스냅샷 로더 (JSON → `SellerRegister` 목록, 프로세스당 1회 캐시)

### 수정 — `app/store.py` 만
`CATALOG_SOURCE == "odoo"` 분기가 있는 곳에 `"snapshot"` 분기를 나란히 추가한다.

| 함수 | 할 일 |
|---|---|
| `sellers_for(item)` | 스냅샷에서 해당 품목의 오퍼 전부 반환 |
| `list_sellers()` | 스냅샷 전체 반환 |
| `list_items()` | 스냅샷의 고유 품목 목록 |
| `register_seller()` | `CatalogReadOnly` 발생 (odoo와 동일 — 카탈로그 주인이 외부다) |

`_offer_to_seller(item, offer)`가 이미 오퍼 dict → `SellerRegister` 변환을 하고 있다.
**새로 만들지 말고 이 함수를 재사용하거나, 스냅샷 스키마를 여기에 맞춰라.**

`set_deal`·`set_approval`의 Odoo 발주서 생성 분기에는 손대지 않는다.
스냅샷 모드는 발주서를 만들지 않는다(외부 ERP가 없다).

### 환경변수
```
CATALOG_SOURCE=snapshot
SNAPSHOT_PATH=data/nexar_snapshot.json
SNAPSHOT_FLOOR_RATIO=0.90     # store.py의 ODOO_FLOOR_RATIO와 같은 관례
```

## 데이터 준비 순서

```bash
export NEXAR_CLIENT_ID=... NEXAR_CLIENT_SECRET=...

python scripts/nexar_snapshot.py --smoke                    # 연결 확인
python scripts/nexar_snapshot.py --introspect SupPartOffer  # MOQ 필드명 확인
# → 확인한 이름을 스크립트 상단 MOQ_FIELD 에 기입
python scripts/nexar_snapshot.py --mpn-file mpns.txt --out data/nexar_snapshot.json
```

`mpns.txt`는 널리 유통되는 범용 부품 20~30개. 스크립트가 마지막에
**판매자가 1곳뿐인 품목을 경고**한다 — 그런 품목은 협상 후보가 안 생기므로 목록에서 뺀다.

## 함정

1. **무료 파트 한도는 조회한 파트 수로 차감된다.** introspection은 차감 없지만
   `supMultiMatch`는 차감된다. 중복 제거는 스크립트가 하지만, **반복 실행 자체를 피할 것.**
   한 번 제대로 돌리고 결과를 커밋한다.
2. **MOQ 필드명은 미확인이다.** GraphQL은 필드 하나만 틀려도 쿼리 전체가 실패한다.
   introspection 먼저. 못 찾으면 `MOQ_FIELD = ""`로 두고 MOQ 없이 간다
   (`negotiate.py`의 MOQ 스크리닝이 `min_qty=None`을 견디는지 확인할 것).
3. **`floor_price`는 합성값이다.** 어떤 공개 데이터에도 없다(공개되면 협상이 성립하지 않는다).
   스냅샷 각 행의 `_synthetic_fields`에 표시돼 있다. **README에 이 경계를 명시할 것** —
   "단가·재고·납기는 실데이터, 원리상 비공개인 유보가격만 합성".
4. **`price_breaks`를 버리지 말 것.** 수량 구간별 단가가 전부 보존돼 있다.
   바이어 요청의 `qty`에 맞는 구간을 골라 쓰면 "500개면 A사, 50개면 B사" 같은
   장면이 공짜로 생긴다. `_offer_to_seller`에서 구간 선택 로직을 넣는 게 자연스럽다.
5. **Octopart API에는 BOM이 없다.** supply 데이터 전용이다.
   `feasibility.py`의 BOM 전개는 계속 Odoo 담당이다. 스냅샷 모드에서 BOM 경로를
   어떻게 처리할지 결정할 것 (가장 단순한 답: 스냅샷 모드는 BOM 전개를 건너뛴다).
